Pull request: Flyway Migration — user_module.email_verification_tokens Table
Requesting closure of issue: #31

Note:
Adds the `user_module.email_verification_tokens` table per Schema doc §1.3. A row is inserted every time a verification email is dispatched — on signup and on manual resend. Once the user clicks the link and the token is consumed, `consumed_at` is set and the token cannot be used again. No service code, no JPA entity, no endpoint — this is the migration only. Also adds `MIGRATIONS.md`, the global Flyway version registry, so future migration PRs use the correct global version number. Migration is forward-only; rollbacks are achieved by writing a corrective forward migration.

**Backend**

* Added `monolith/src/main/resources/db/migration/user_module/V3__create_email_verification_tokens.sql`:
  * **Version 3** in the global Flyway sequence (V1 = `user_module.users` in v0.2-001, V2 = `auth.refresh_tokens` in v0.2-003)
  * Creates `user_module.email_verification_tokens` with all columns per Schema doc §1.3
  * Uses the existing `user_module` schema (created in v0.2-001)

* Column list:
  * `id` — `UUID PRIMARY KEY` (UUID v7 generated at the application layer; no `DEFAULT` clause)
  * `user_id` — `UUID NOT NULL` with `FOREIGN KEY REFERENCES user_module.users(id) ON DELETE CASCADE`
  * `token_hash` — `VARCHAR(255) NOT NULL UNIQUE` (SHA-256 hex of the plaintext token embedded in the verification URL)
  * `expires_at` — `TIMESTAMPTZ NOT NULL` (set by application: `created_at + 24 hours` at dispatch time)
  * `consumed_at` — `TIMESTAMPTZ` nullable (`NULL` = unused; non-`NULL` = consumed and cannot be reused)

* Design decisions documented in the migration:
  * No `created_at` column — not required by any query; `expires_at` minus 24h would recover it if ever needed via a forward migration
  * `token_hash` stores the digest only; plaintext token is in the email URL and never persisted server-side (same pattern as `auth.refresh_tokens`)
  * `consumed_at` is the single-use gate; expired tokens are rejected even when `consumed_at IS NULL`

* Indexes per Schema doc §1.3:
  * `email_verification_tokens_token_hash_unique` — `UNIQUE (token_hash)`
  * `email_verification_tokens_user_id_consumed_at_idx` — `BTREE (user_id, consumed_at)` (resend-rate-limit and unconsumed-token lookups)

* Added `monolith/src/main/resources/db/migration/MIGRATIONS.md`:
  * Documents that Flyway version numbers are **global** across all migration folders
  * Registry table: V1–V5 mapped to issue, file path, and table
  * Filename convention and forward-only rollback rule
  * **Next free version** guidance for subsequent migration PRs

* No JPA entity, repository, or service code in this PR — those ship in later auth issues

**Tests**

* `EmailVerificationTokensMigrationTest` — Testcontainers Postgres test that applies all migrations against a fresh database and verifies:
  * `user_module.email_verification_tokens` table exists
  * Every column from Schema doc §1.3 is present with the correct data type and nullability (`id`, `user_id`, `token_hash`, `expires_at`, `consumed_at`)
  * No `created_at` column is present (intentional omission per migration design)
  * The composite index on `(user_id, consumed_at)` exists
  * The unique constraint on `token_hash` (`email_verification_tokens_token_hash_unique`) is registered
  * The foreign key from `user_id` to `user_module.users(id)` with `ON DELETE CASCADE` is registered

* `EmailVerificationTokensConstraintsTest` — Testcontainers Postgres test that verifies behavioral constraints:
  * Inserting a token referencing a non-existent `user_id` fails with a foreign-key violation
  * Inserting two tokens with the same `token_hash` fails with a unique-constraint violation
  * Inserting a valid token with `consumed_at = NULL` succeeds (active, unconsumed token)
  * Inserting a second token for the same user with a different `token_hash` succeeds
  * Deleting a user via `DELETE FROM user_module.users WHERE id = ?` cascades and removes all of that user's verification tokens (`ON DELETE CASCADE` from `user_id`)
  * Updating `consumed_at` to a non-null value on an existing row succeeds (consumption path)

**Important — `docker compose up` does NOT start the Spring Boot services**

`docker compose up -d` starts Postgres and RabbitMQ only. The monolith must be started manually via `mvn spring-boot:run` to trigger Flyway. The verification steps below will not produce the migrated schema if the monolith is not started.

**Prerequisites:** JDK **21** (project target) and **Docker** running (Testcontainers needs it for Step 8). Branch must include v0.2-001 (V1) and v0.2-003 (V2) migrations.

**How to verify**

**Step 1 — Start monolith-db on a clean state**

If `monolith-db` is already running from previous work, recreate it so Flyway runs against an empty database.

From the repo root:

Linux/Mac:
```bash
docker compose down -v
docker compose up monolith-db -d
```
Windows (PowerShell):
```powershell
docker compose down -v
docker compose up monolith-db -d
```

Wait for `monolith-db` to reach a healthy state.

**Step 2 — Start the monolith and trigger Flyway**

Open a new terminal.

From the repo root:

Linux/Mac:
```bash
cd monolith
mvn spring-boot:run
```
Windows (PowerShell):
```powershell
cd monolith
mvn spring-boot:run
```

Watch the logs for Flyway output. Confirm migration **version 3** is applied (description: `create email verification tokens`). Flyway tracks versions in `public.flyway_schema_history` — not per PostgreSQL schema. Versions 1 (`user_module.users`), 2 (`auth.refresh_tokens`), and 3 (`email_verification_tokens`) should all appear as applied.

**Step 3 — Confirm the table exists**

Open a new terminal.

Connect to `monolith-db`:

Linux/Mac:
```bash
docker exec -it $(docker ps --filter "name=monolith-db" --format "{{.Names}}") psql -U stash_monolith -d monolith_db
```
Windows (PowerShell):
```powershell
docker exec -it (docker ps --filter "name=monolith-db" --format "{{.Names}}") psql -U stash_monolith -d monolith_db
```

Then run:
```sql
\d user_module.email_verification_tokens
```

Confirm the table shows all 5 columns from Schema doc §1.3 with correct types, the foreign key to `user_module.users`, and no `created_at` column.

**Step 6 — Confirm the foreign key cascade**

While still connected via `psql`:

```sql
INSERT INTO user_module.users (id, email, password_hash, display_name)
VALUES ('018f1234-1234-7000-8000-000000000001', 'cascade@example.com', 'x', 'CascadeUser');

INSERT INTO user_module.email_verification_tokens (id, user_id, token_hash, expires_at)
VALUES (
  '018f1234-1234-7000-8000-000000000002',
  '018f1234-1234-7000-8000-000000000001',
  'hash-ev-cascade-test',
  now() + INTERVAL '24 hours'
);

SELECT count(*) FROM user_module.email_verification_tokens
WHERE user_id = '018f1234-1234-7000-8000-000000000001';
-- Expect: 1

DELETE FROM user_module.users WHERE id = '018f1234-1234-7000-8000-000000000001';

SELECT count(*) FROM user_module.email_verification_tokens
WHERE user_id = '018f1234-1234-7000-8000-000000000001';
-- Expect: 0
```

Confirm the second `count(*)` returns `0` — the token was cascade-deleted with the user.

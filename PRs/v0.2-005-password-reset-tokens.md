Pull request: Flyway Migration — user_module.password_reset_tokens Table
Requesting closure of issue: #32

Note:
Adds the `user_module.password_reset_tokens` table for the password-reset flow (v0.2-016, v0.2-017). A row is inserted every time a user requests a password reset. The raw token is never stored — only its SHA-256 hash. Tokens expire after 1 hour and can only be consumed once. Also updates the Schema doc with §1.5 (`password_reset_tokens`) and adds `MIGRATIONS.md` if not already present from v0.2-004. No service code, no JPA entity, no endpoint — this is the migration only. Migration is forward-only; rollbacks are achieved by writing a corrective forward migration.

**Backend**

* Added `monolith/src/main/resources/db/migration/user_module/V4__create_password_reset_tokens.sql`:
  * **Version 4** in the global Flyway sequence (V1 = `user_module.users`, V2 = `auth.refresh_tokens`, V3 = `email_verification_tokens`)
  * Creates `user_module.password_reset_tokens`
  * Uses the existing `user_module` schema (created in v0.2-001)

* Column list:
  * `id` — `UUID PRIMARY KEY` (UUID v7 generated at the application layer; no `DEFAULT` clause)
  * `user_id` — `UUID NOT NULL` with `FOREIGN KEY REFERENCES user_module.users(id) ON DELETE CASCADE`
  * `token_hash` — `VARCHAR(255) NOT NULL UNIQUE` (SHA-256 hex of the plaintext token embedded in the reset URL)
  * `expires_at` — `TIMESTAMPTZ NOT NULL` (set by application: `created_at + 1 hour` at dispatch time)
  * `consumed_at` — `TIMESTAMPTZ` nullable (`NULL` = unused; non-`NULL` = consumed and cannot be reused)

* Design decisions documented in the migration:
  * Mirrors `email_verification_tokens` structure: same SHA-256 hash pattern, same single-use gate via `consumed_at`
  * 1-hour expiry (vs 24h for email verification)
  * No `created_at` column — derivable from `expires_at - 1 hour`; omitted to keep the table minimal
  * `token_hash` stores the digest only; plaintext token is in the reset URL and never persisted server-side

* Indexes:
  * `password_reset_tokens_token_hash_unique` — `UNIQUE (token_hash)`
  * `password_reset_tokens_active_idx` — `BTREE (user_id, expires_at) WHERE consumed_at IS NULL` (partial index for active-token lookup and rate-limit checks)

* Added `monolith/src/main/resources/db/migration/MIGRATIONS.md` (if not already on `develop` from v0.2-004):
  * Documents that Flyway version numbers are **global** across all migration folders
  * Registry table: V1–V5 mapped to issue, file path, and table
  * Filename convention and forward-only rollback rule

* Updated `docs/architecture/Stash Database Schema Design.docx`:
  * Adds `password_reset_tokens` table definition as Schema doc §1.5 (single source of truth)

* No JPA entity, repository, or service code in this PR — those ship in v0.2-016 and v0.2-017

**Tests**

* `PasswordResetTokensMigrationTest` — Testcontainers Postgres test that applies all migrations against a fresh database and verifies:
  * `user_module.password_reset_tokens` table exists
  * Every column is present with the correct data type and nullability (`id`, `user_id`, `token_hash`, `expires_at`, `consumed_at`)
  * No `created_at` column is present (intentional omission per migration design)
  * The partial index on `(user_id, expires_at) WHERE consumed_at IS NULL` exists (`password_reset_tokens_active_idx`)
  * The unique constraint on `token_hash` (`password_reset_tokens_token_hash_unique`) is registered
  * The foreign key from `user_id` to `user_module.users(id)` with `ON DELETE CASCADE` is registered

* `PasswordResetTokensConstraintsTest` — Testcontainers Postgres test that verifies behavioral constraints:
  * Inserting a token referencing a non-existent `user_id` fails with a foreign-key violation
  * Inserting two tokens with the same `token_hash` fails with a unique-constraint violation
  * Inserting a valid token with `consumed_at = NULL` succeeds (active, unconsumed token)
  * Inserting a second token for the same user with a different `token_hash` succeeds
  * Deleting a user via `DELETE FROM user_module.users WHERE id = ?` cascades and removes all of that user's reset tokens (`ON DELETE CASCADE` from `user_id`)
  * Updating `consumed_at` to a non-null value on an existing row succeeds (consumption path)

**Important — `docker compose up` does NOT start the Spring Boot services**

`docker compose up -d` starts Postgres and RabbitMQ only. The monolith must be started manually via `mvn spring-boot:run` to trigger Flyway. The verification steps below will not produce the migrated schema if the monolith is not started.

**Prerequisites:** JDK **21** (project target) and **Docker** running (Testcontainers needs it for Step 8). Branch must include v0.2-001 (V1), v0.2-003 (V2), and v0.2-004 (V3) migrations.

**How to verify**

**Step 1 — Start monolith-db on a clean state**

If `monolith-db` is already running from previous work, recreate it so Flyway runs against an empty database.

From the repo root:

Linux/Mac:
```bash
docker compose down -v
docker compose up monolith-db -d
```
Windows (PowerShell):
```powershell
docker compose down -v
docker compose up monolith-db -d
```

Wait for `monolith-db` to reach a healthy state.

**Step 2 — Start the monolith and trigger Flyway**

Open a new terminal.

From the repo root:

Linux/Mac:
```bash
cd monolith
mvn spring-boot:run
```
Windows (PowerShell):
```powershell
cd monolith
mvn spring-boot:run
```

Watch the logs for Flyway output. Confirm migration **version 4** is applied (description: `create password reset tokens`). Flyway tracks versions in `public.flyway_schema_history` — not per PostgreSQL schema. Versions 1–4 should all appear as applied.

**Step 3 — Confirm the table exists**

Open a new terminal.

Connect to `monolith-db`:

Linux/Mac:
```bash
docker exec -it $(docker ps --filter "name=monolith-db" --format "{{.Names}}") psql -U stash_monolith -d monolith_db
```
Windows (PowerShell):
```powershell
docker exec -it (docker ps --filter "name=monolith-db" --format "{{.Names}}") psql -U stash_monolith -d monolith_db
```

Then run:
```sql
\d user_module.password_reset_tokens
```

Confirm the table shows all 5 columns with correct types, the foreign key to `user_module.users`, and no `created_at` column.

**Step 4 — Confirm the indexes**

While still connected via `psql`:
```sql
\di user_module.password_reset_tokens*
```

Confirm the expected indexes are listed:
* The primary key on `id`
* The unique index on `token_hash`
* The partial index on `(user_id, expires_at) WHERE consumed_at IS NULL`

**Step 5 — Confirm Flyway history**

While still connected via `psql`:
```sql
SELECT version, description, success FROM flyway_schema_history ORDER BY installed_rank;
```

Confirm rows for versions 1, 2, 3, and 4 are all present with `success = t`.

**Step 6 — Confirm the foreign key cascade**

While still connected via `psql`:

```sql
INSERT INTO user_module.users (id, email, password_hash, display_name)
VALUES ('018f1234-1234-7000-8000-000000000001', 'cascade@example.com', 'x', 'CascadeUser');

INSERT INTO user_module.password_reset_tokens (id, user_id, token_hash, expires_at)
VALUES (
  '018f1234-1234-7000-8000-000000000002',
  '018f1234-1234-7000-8000-000000000001',
  'hash-pr-cascade-test',
  now() + INTERVAL '1 hour'
);

SELECT count(*) FROM user_module.password_reset_tokens
WHERE user_id = '018f1234-1234-7000-8000-000000000001';
-- Expect: 1

DELETE FROM user_module.users WHERE id = '018f1234-1234-7000-8000-000000000001';

SELECT count(*) FROM user_module.password_reset_tokens
WHERE user_id = '018f1234-1234-7000-8000-000000000001';
-- Expect: 0
```

Confirm the second `count(*)` returns `0` — the token was cascade-deleted with the user.

**Step 7 — Confirm the unique constraint on token_hash**

While still connected via `psql`:

```sql
INSERT INTO user_module.users (id, email, password_hash, display_name)
VALUES ('018f1234-1234-7000-8000-000000000003', 'unique@example.com', 'x', 'UniqueUser');

INSERT INTO user_module.password_reset_tokens (id, user_id, token_hash, expires_at)
VALUES (
  '018f1234-1234-7000-8000-000000000004',
  '018f1234-1234-7000-8000-000000000003',
  'hash-duplicate-test',
  now() + INTERVAL '1 hour'
);

INSERT INTO user_module.password_reset_tokens (id, user_id, token_hash, expires_at)
VALUES (
  '018f1234-1234-7000-8000-000000000005',
  '018f1234-1234-7000-8000-000000000003',
  'hash-duplicate-test',
  now() + INTERVAL '1 hour'
);
```

Confirm the second insert fails with a unique-constraint violation on `token_hash`.

Clean up:
```sql
DELETE FROM user_module.users WHERE email = 'unique@example.com';
\q
```

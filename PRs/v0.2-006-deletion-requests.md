Pull request: Flyway Migration — user_module.deletion_requests Table
Requesting closure of issue: #33

Note:
Adds the `user_module.deletion_requests` table per Schema doc §1.4. When a user requests account deletion, a row is inserted with `scheduled_completion_at` set 30 days in the future. The actual cleanup job that processes due rows ships in v0.5 — this issue only creates the table. No service code, no JPA entity, no endpoint — this is the migration only. Migration is forward-only; rollbacks are achieved by writing a corrective forward migration.

**Backend**

* Added `monolith/src/main/resources/db/migration/user_module/V5__create_deletion_requests.sql`:
  * **Version 5** in the global Flyway sequence (V1–V4 = prior user/auth migrations; see `MIGRATIONS.md`)
  * Creates `user_module.deletion_requests`
  * Uses the existing `user_module` schema (created in v0.2-001)

* Column list:
  * `id` — `UUID PRIMARY KEY` (UUID v7 generated at the application layer; no `DEFAULT` clause)
  * `user_id` — `UUID NOT NULL` with `FOREIGN KEY REFERENCES user_module.users(id) ON DELETE RESTRICT`
  * `status` — `VARCHAR(50) NOT NULL DEFAULT 'PENDING'` with CHECK: `PENDING`, `COMPLETED`, `CANCELLED`
  * `blockers_at_submission` — `JSONB` nullable (snapshot of active blockers at request time for ops audit trail)
  * `submitted_at` — `TIMESTAMPTZ NOT NULL DEFAULT NOW()`
  * `scheduled_completion_at` — `TIMESTAMPTZ NOT NULL` (set by application: `submitted_at + 30 days`)
  * `completed_at` — `TIMESTAMPTZ` nullable (set when deletion is executed)
  * `cancelled_at` — `TIMESTAMPTZ` nullable (set when user cancels during cool-off)

* Design decisions documented in the migration:
  * `ON DELETE RESTRICT` on `user_id` — deletion requests are auditable records; hard-deleting a user with a pending request requires closing the request first
  * `blockers_at_submission` as JSONB — blocker shape varies (susu groups, vaults, splits); avoids schema churn as new blocker types are added
  * `status` as VARCHAR + CHECK (not Postgres ENUM) — same rationale as other status columns; no `ALTER TYPE` lock
  * Partial `EXCLUDE` constraint `deletion_requests_one_pending_per_user` — at most one `PENDING` request per user at the database level (also enforced in application layer in v0.2-019)

* Indexes:
  * `deletion_requests_cleanup_job_idx` — `BTREE (scheduled_completion_at) WHERE status = 'PENDING'` (partial index for the v0.5 daily cleanup job)
  * `deletion_requests_user_id_idx` — `BTREE (user_id)` (supports "my deletion request" screen)

* Updated `monolith/src/main/resources/db/migration/MIGRATIONS.md`:
  * Adds V5 row (`user_module.deletion_requests`) to the global version registry

* No JPA entity, repository, or deletion service code in this PR — those ship in v0.2-019 and v0.5

**Tests**

* `DeletionRequestsMigrationTest` — Testcontainers Postgres test that applies all migrations against a fresh database and verifies:
  * `user_module.deletion_requests` table exists
  * Every column from Schema doc §1.4 is present with the correct data type and nullability
  * `blockers_at_submission` is `JSONB`
  * The `status` CHECK constraint accepts `PENDING`, `COMPLETED`, `CANCELLED`
  * The partial index on `(scheduled_completion_at) WHERE status = 'PENDING'` exists (`deletion_requests_cleanup_job_idx`)
  * The supporting index on `user_id` exists (`deletion_requests_user_id_idx`)
  * The foreign key from `user_id` to `user_module.users(id)` with `ON DELETE RESTRICT` is registered
  * The partial `EXCLUDE` constraint `deletion_requests_one_pending_per_user` is registered

* `DeletionRequestsConstraintsTest` — Testcontainers Postgres test that verifies behavioral constraints:
  * Inserting a request referencing a non-existent `user_id` fails with a foreign-key violation
  * Inserting a valid `PENDING` request with `blockers_at_submission = '{}'::jsonb` succeeds
  * Inserting a second `PENDING` request for the same user fails (partial EXCLUDE constraint)
  * Inserting a request with `status = 'INVALID'` fails with a CHECK violation
  * Deleting a user who has a `PENDING` deletion request fails (`ON DELETE RESTRICT`)
  * Cancelling a request (`status = 'CANCELLED'`) then inserting a new `PENDING` request for the same user succeeds
  * The partial index `deletion_requests_cleanup_job_idx` is present in `pg_indexes` with the correct `WHERE status = 'PENDING'` predicate
  * `EXPLAIN` on the v0.5 cleanup query against a seeded dataset shows an index scan on `deletion_requests_cleanup_job_idx` (satisfies issue DoD):
    ```sql
    EXPLAIN (FORMAT TEXT)
    SELECT id FROM user_module.deletion_requests
    WHERE status = 'PENDING' AND scheduled_completion_at <= NOW();
    ```

**Important — `docker compose up` does NOT start the Spring Boot services**

`docker compose up -d` starts Postgres and RabbitMQ only. The monolith must be started manually via `mvn spring-boot:run` to trigger Flyway. The verification steps below will not produce the migrated schema if the monolith is not started.

**Prerequisites:** JDK **21** (project target) and **Docker** running (Testcontainers needs it for Step 9). Branch must include migrations V1 through V4.

**How to verify**

**Step 1 — Start monolith-db on a clean state**

If `monolith-db` is already running from previous work, recreate it so Flyway runs against an empty database.

From the repo root:

Linux/Mac:
```bash
docker compose down -v
docker compose up monolith-db -d
```
Windows (PowerShell):
```powershell
docker compose down -v
docker compose up monolith-db -d
```

Wait for `monolith-db` to reach a healthy state.

**Step 2 — Start the monolith and trigger Flyway**

Open a new terminal.

From the repo root:

Linux/Mac:
```bash
cd monolith
mvn spring-boot:run
```
Windows (PowerShell):
```powershell
cd monolith
mvn spring-boot:run
```

Watch the logs for Flyway output. Confirm migration **version 5** is applied, e.g.:

`Migrating schema "user_module" to version "5 - create deletion requests"`

Pull request: Refresh-Token Service with Rotation and Replay Detection
Requesting closure of issue: #36

Note:
Introduces `RefreshTokenService` — the most security-critical piece of the v0.2 auth system. Refresh tokens are long-lived (7 days), rotated on every use, and stored only as SHA-256 hashes. When a previously rotated token is presented again, the service walks the `replaced_by_id` chain forward and revokes every descendant in a single transaction, then emits a `RefreshTokenReplayDetected` event to RabbitMQ for the notification worker (v0.5). Raw token values are never stored or logged. No HTTP endpoints in this PR — `POST /api/v1/auth/login`, `/refresh`, and `/logout` ship in v0.2-011, v0.2-014, and v0.2-015 and will call this service.

**Backend**

* Added `monolith/src/main/java/com/stash/platform/user/service/RefreshTokenService.java`:
  * **`issue(User, deviceId, deviceLabel, ipAddress)`** — generates a cryptographically random 256-bit token, stores SHA-256 hex hash in `auth.refresh_tokens`, returns `TokenPair(accessToken, rawRefreshToken)`; access token issued via `JwtTokenService`
  * **`refresh(rawRefreshToken, deviceId, deviceLabel, ipAddress)`** — hash lookup; rejects expired tokens; on revoked token triggers replay handling; on valid token atomically rotates (revoke old with `ROTATION` reason + `replaced_by_id` link, insert new, return new pair)
  * **`revoke(rawRefreshToken)`** — user-initiated logout; idempotent; sets `USER_LOGOUT` reason
  * **`revokeAllForUser(userId, reason)`** — bulk revocation (e.g. password reset); uses caller-supplied reason (`ADMIN_FORCE`, etc.)
  * Token format: 32 random bytes → Base64url (no padding) plaintext returned once; SHA-256 hex persisted
  * Expiry: 7 days from issue (`created_at + 7 days`)
  * Revocation reason constants: `ROTATION`, `ROTATION_REPLAY`, `USER_LOGOUT`, `ADMIN_FORCE` (must match migration CHECK constraint)

* Replay attack handling (`handleReplayAttack`):
  * Triggered when a revoked token is presented for refresh
  * Recursively walks `replaced_by_id` chain forward from the replayed token via `findByReplacedById`
  * Revokes every unrevoked descendant with `ROTATION_REPLAY` reason — all within the calling `@Transactional` boundary (no partial revocations)
  * Publishes `RefreshTokenReplayDetectedEvent` to exchange `monolith.events`, routing key `auth.refresh_token.replay_detected`
  * RabbitMQ publish failure is non-fatal (revocations already committed in transaction scope)

* Added `monolith/src/main/java/com/stash/platform/user/domain/RefreshToken.java`:
  * JPA entity for `auth.refresh_tokens` per Schema doc §1.1
  * Domain helpers: `isActive()`, `isExpired()`, `isRevoked()`, `revoke(reason)`
  * UUID v7 IDs via `UuidV7Generator`

* Added `monolith/src/main/java/com/stash/platform/user/repository/RefreshTokenRepository.java`:
  * `findByTokenHash(String)` — hash lookup for refresh/revoke
  * `findByReplacedById(UUID)` — chain-walk for replay detection
  * `findActiveByUserId(UUID)` — bulk revocation

* Added `monolith/src/main/java/com/stash/platform/user/event/RefreshTokenReplayDetectedEvent.java`:
  * Event record: `eventId`, `eventType`, `schemaVersion`, `sourceService`, `occurredAt`, `correlationId`, `payload`
  * Payload: `userId`, `replayedTokenId`, `descendantsRevoked`
  * Consumed by notification worker in v0.5 (not in this PR)

* Added `monolith/src/main/java/com/stash/platform/user/exception/RefreshTokenException.java`:
  * Extends `StashApiException` with `ErrorCode.AUTH_TOKEN_INVALID` and HTTP 401

* Security invariants:
  * Raw token bytes never logged, stored, or included in exceptions
  * Only SHA-256 hex hash persisted in `auth.refresh_tokens.token_hash`
  * Raw token returned to caller exactly once per issue/refresh

* Dependencies (prior PRs — not introduced here):
  * `auth.refresh_tokens` table (v0.2-003 / Flyway V2)
  * `User` entity + `UserRepository.findByIdIncludingDeleted` (v0.2-002)
  * `JwtTokenService` (v0.2-008)
  * `RabbitTemplate` (existing Spring AMQP config)

* No new Maven dependencies

**Tests**

* `RefreshTokenServiceTest` — `@SpringBootTest` integration tests with Testcontainers Postgres; `RabbitTemplate` mocked:
  * **`issue()`**
    * Returns a non-null token pair (access JWT + raw refresh token)
    * Persists SHA-256 hash, not plaintext — stored hash ≠ raw token and does not contain it
  * **`refresh()` — happy path**
    * Returns a new token pair on valid token
    * Old token revoked with `ROTATION` reason and `replaced_by_id` set
    * Two rows exist after one rotation (old revoked + new active)
  * **`refresh()` — failure cases**
    * Throws `RefreshTokenException` for unknown token
    * Throws `RefreshTokenException` for expired token
    * Throws `RefreshTokenException` for a directly revoked token (logout)
  * **Replay detection**
    * Presenting a rotated token after a 3-token chain (issue → refresh → refresh) revokes all 3 tokens
    * Descendants revoked with `ROTATION_REPLAY` reason
    * Replay event published to RabbitMQ (`convertAndSend` verified)
  * **Security: raw token must not appear in logs** (issue DoD negative test)
    * Raw refresh token not present in any log message during `issue()` or `refresh()`

**Step 1 — Run the integration tests**

From the repo root:

Linux/Mac:
```bash

```
Windows (PowerShell):
```powershell
mvn clean test -pl monolith "-Dtest=RefreshTokenServiceTest"
```

Confirm all nested test groups pass:
* `issue()` — token pair returned, hash stored not plaintext
* `refresh() — happy path` — rotation, `ROTATION` reason, two rows
* `refresh() — failure cases` — unknown, expired, revoked
* `replay detection` — full chain revocation, `ROTATION_REPLAY` reason, RabbitMQ event
* `security: raw token must not appear in logs`

Use `clean` to avoid stale `target/` artifacts from other branches.

**Step 2 — Performance spot-check (optional, issue DoD)**

If validating the < 100ms target on a warm connection pool:

1. Ensure `monolith-db` is running and migrations V1–V2 are applied
2. Start the monolith with `local` profile
3. Issue a token pair via a scratch call or future login endpoint
4. Time several consecutive `refresh()` calls on the same session chain

Expect each refresh exchange to complete in under 100ms once the connection pool is warm. This is not automated on the branch.

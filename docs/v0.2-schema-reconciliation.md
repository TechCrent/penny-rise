# v0.2 Schema ↔ Issue Plan Reconciliation

The canonical **Schema doc §8** lists three KYC tables. The v0.2 Issue Plan (issues 020–027) requested additional structures. This document records what was **built in code** and how it maps to the Schema doc, so v0.3 does not re-debate canonical names.

## Canonical Schema doc §8 (three tables)

| Schema doc name | Implemented as | Migration |
|-----------------|----------------|-----------|
| `kyc_submissions` | `kyc.submissions` | `submission/V1__create_kyc_submissions.sql` |
| `kyc_documents` | `kyc.submission_documents` | `document/V1.1__create_kyc_submission_documents.sql` |
| `kyc_deletion_attempts` | `kyc.document_deletion_jobs` | `document/V1.2__create_kyc_document_deletion_jobs.sql` |

Naming differs slightly (`submission_documents` vs `kyc_documents`) but roles match.

## Extra tables (Issue Plan, not in Schema §8)

Built intentionally for v0.2; **accepted as extensions** until Schema doc §8 is updated in a future architecture revision.

| Issue Plan concept | Table | Purpose | Migration |
|--------------------|-------|---------|-----------|
| `provider_decisions` | `kyc.provider_decisions` | Append-only log of automated provider responses | `submission/V2__create_kyc_provider_decisions.sql` |
| `manual_review_queue` | `kyc.manual_review_queue` | Admin queue rows for manual review path | `submission/V3__create_kyc_manual_review_queue.sql` |
| `processed_document_events` | `kyc.processed_document_events` | Idempotency for document confirm webhooks | `document/V1.3__create_processed_document_events.sql` |

Each migration file includes a `NOTE: NOT in canonical Schema doc §8` comment.

## Design decisions folded into `kyc.submissions`

The Issue Plan's separate `provider_decisions` **current-state** view is represented on `kyc.submissions` columns:

- `provider_decision`, `provider_reference`, `review_path`

The separate `provider_decisions` table is the **append-only audit** of provider calls, not the sole source of truth for submission status.

## Deletion model

Issue Plan "document deletion jobs" maps to:

- **Work queue:** `kyc.submission_documents` rows with `deletion_status IN ('PENDING_DELETION', 'DELETE_FAILED')` and `deletion_scheduled_at <= now()` (see v0.2-027 worker)
- **Audit trail:** `kyc.document_deletion_jobs` (Schema §8.3 `kyc_deletion_attempts`)

No separate standalone jobs table beyond the audit append log.

## Status enum reconciliation

`PENDING_DOCUMENTS` was added in `submission/V4__add_pending_documents_status.sql` for the two-phase upload flow (create → upload docs → finalize). Schema doc sign-off pending; code and mobile E2E rely on this state.

## Monolith vs KYC status naming

| Layer | Terminal approve status |
|-------|-------------------------|
| `kyc.submissions.status` | `APPROVED` |
| `users.kyc_status` (monolith) | `APPROVED` |

Early issue javadoc referenced `VERIFIED` for monolith; **code uses `APPROVED`** everywhere. Event javadocs were aligned in Tier 3.

## API route convention

| Client | Canonical poll route | Notes |
|--------|---------------------|-------|
| Mobile (via monolith proxy) | `GET /api/v1/kyc/submissions/me` | Resumability, post-login routing |
| Mobile (specific submission) | `GET /api/v1/kyc/submissions/{id}` | Step 3 polling after user knows ID |
| Admin console | Direct kyc-service `:8082` | Same paths, admin JWT |

## HTTP status convention (System Design §6.3)

| Case | Status | Handler |
|------|--------|---------|
| Bean Validation (`@Valid`, `@Pattern`, etc.) | **400** | `GlobalExceptionHandler` |
| Semantic business rule (e.g. reject without reason) | **422** | `StashApiException` with `UNPROCESSABLE_ENTITY` |

OpenAPI `@ApiResponse` annotations were aligned to match in Tier 3.
